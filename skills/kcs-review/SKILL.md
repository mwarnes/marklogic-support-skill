name: kcs-review
description: Review a KCS article written by another engineer (md/html/docx or pasted text) and write the revised article as Markdown, Word and Salesforce HTML. Use when the user runs /kcs-review or asks to review a KCS article.
argument-hint: [path to article]
---

This is the `/kcs-review` workflow the user's own team maintains for reviewing a Knowledge-Centered Support article that another engineer sent for review (see the `kcs` skill, which writes articles from a ticket). It checks the article against the team's 20-field format, the Solution Content Standard rules in `kcs-writing.md`, and sanitisation rules, summarises recommendations, and on acceptance writes the revised article as Markdown, Word and Salesforce HTML. Imperative wording below is only there so steps are executed rather than narrated.

Article path argument (optional, may contain spaces): $ARGUMENTS

(If the line above is empty or still shows a `$`-placeholder instead of a value, the user gave no path in this invocation; if they gave one in their message, for example `/skill:kcs-review path/to/article.md`, use that.)

1. **Load the skill material.** **Locate the `marklogic-support` skill directory** (it holds `SKILL.md`, `references/` and `scripts/`; call it `<skill-dir>`). First look for the `marklogic-support` folder that sits next to this skill's own folder, i.e. `../marklogic-support` relative to the folder this SKILL.md was loaded from (in Claude Code that is `${CLAUDE_SKILL_DIR}/../marklogic-support`); if it exists, use it. Otherwise check, in this order, and use the first that exists: `~/.agents/skills/marklogic-support`, `~/.claude/skills/marklogic-support`, `~/.copilot/skills/marklogic-support`, then in the project (the current directory and its parents up to the repository root) `.agents/skills/marklogic-support`, `.claude/skills/marklogic-support`, `.github/skills/marklogic-support`, then `skills/marklogic-support` if this repository is checked out. Do not search the filesystem. If none exists (or a symlink is broken), tell the user the skill is not installed and that the repository README explains how to install it, then stop. Read `<skill-dir>/references/kcs-writing.md`. Use its "Reviewing an article" section as the checklist.

2. **Get the article.**
   - If the article path argument above is non-empty, the whole of it is the path (do not split on spaces). Otherwise ask in plain chat text: "Give me the path to the KCS article (.md, .html or .docx), or paste the article text here." Wait for the reply.
   - A path: run (shell tool) `python3 "<skill-dir>/scripts/kcs_render.py" --to-md "<path>"` and use its stdout as the article Markdown. If it fails (file not found, unsupported type, pandoc missing for html/docx), show the error, and ask again — for pandoc missing, also offer that the user can paste the text instead.
   - Pasted text: treat it as Markdown as-is.
   - Keep the original untouched; all edits are made to your working copy.

3. **Review** the working copy against the checklist: the 20 `## ` headings in order, the four-line Environment section, sanitisation (the ticket number must appear nowhere), the SCS field rules (title and summary length, URL Name derived from the Title, `MLE-<number>` ids, Article Category, manual-only Internal Comments and Admin Ticket ID, standard Cause and Resolution statements, style and links), the security/CVE and alert checks (a security vulnerability or CVE article must carry the `INTERNAL` prefix and Area of Interest `Security`; the word "breach" in any form is a must-fix; a TSE may edit a security vulnerability article only after consulting the original author or a security subject-matter expert — remind the user of this when proposing edits to one), consistency, and technical accuracy against the skill's reference files, and the type banner: the Markdown must start with the `<!-- KCS ARTICLE — <type> ... -->` comment from `kcs-writing.md` (`Problem/Solution`, `How-To (framed as Problem/Solution per template constraints)`, or `How to troubleshoot`) matching the article's real type. Imports from .html/.docx always lose it, so treat a missing or wrong banner as should-fix. Do not invent facts to fill gaps and do not silently correct anything you cannot verify — report it as "could not verify". An article in the earlier 18-field format (no Internal Comments or Article Category, Summary after Validation Status) is a should-fix, not a must-fix: add the Internal Comments (`*(manual entry)*`) and Article Category (derived) placeholders, move Summary above Validation Status, and report that you did.

4. **Summarise** the findings in plain chat text, grouped **must-fix**, **should-fix**, **optional**, each with the field it applies to and the proposed change. Then ask: "Accept these recommendations?" (yes / no).

5. **Decide** (all-or-nothing).
   - **Yes:** apply every recommendation to the working copy, show the full revised article, and ask the user to confirm it. Apply edits and re-show if they ask for more.
   - **No:** ask in plain chat text which parts need correction or improvement. Revise accordingly, re-summarise what changed, and go back to the "Accept?" question.

6. **Write** once the user has confirmed the revised article.
   - Take the title from the `## Title` field of the revised article. Run `python3 "<skill-dir>/scripts/kcs_render.py" --target "<title>"`; its output is the target path without extension (`kcs-drafts/` in the current directory if it exists, otherwise the current directory; existing files get a numeric suffix).
   - The revised Markdown must begin with the banner comment exactly as in `kcs-writing.md` (`<!--`, `KCS ARTICLE — Problem/Solution`, `KCS ARTICLE — How-To (framed as Problem/Solution per template constraints)` or `KCS ARTICLE — How to troubleshoot`, `Paste each section below into the matching Salesforce field.`, `-->`) with the correct article type; re-add it if the import lost it. The renderer reads the type from that line and otherwise guesses from the filename.
   - Write the revised Markdown to `<target>.md` and run `python3 "<skill-dir>/scripts/kcs_render.py" "<target>.md"`. If the renderer rejects the article (headings, Environment or an `SCS content errors` line), fix the Markdown, show the user what you changed, and re-run. If pandoc is missing, tell the user the `.md` is finished and how to install pandoc; do not hand-write the other formats. Show the user any `warning:` lines the renderer printed.
   - Confirm with `ls` that the `.md`, `.docx` and `.html` exist, then list the three file paths. Do not modify or delete the original article. Do not write ticket audit-trail entries. Remind the user of the manual Salesforce steps: Admin Ticket ID, Internal Comments, set Area of Interest if it was left empty, Smart Links for the listed article titles, attachments/images, and Channels.
