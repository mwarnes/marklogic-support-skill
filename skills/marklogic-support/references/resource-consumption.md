# MarkLogic resource consumption: ingest, merges, indexes, queries and operations

Use for any performance, tuning, capacity or "what is using the disk, CPU, memory or network" ticket. It says which MarkLogic activity uses which resource, what is normal, and what a symptom usually points at.

**Version warning.** The source is the MarkLogic whitepaper "Understanding System Resources" (E. Miller, January 2016), written for MarkLogic 7 and 8. The skill targets 11 and 12. The mechanisms are the foundation of the product; hard numbers, defaults, message names and platform notes may have changed. Numbers below are tagged `[unverified — confirm for 11/12]` and must be checked against the current documentation before they are quoted to a customer. "RC p.N" is the printed page of the paper (see Sources). The text is paraphrased, never quoted.

## Concepts

- **E-node and D-node.** Any host can be an E-node (has app servers, no forests), a D-node (has forests, no app servers) or both. E-nodes parse requests, run XQuery/JavaScript/XSLT/SPARQL/SQL, expand documents, filter, aggregate and tokenise at load. D-nodes hold data and indexes, resolve indexes, read and write forests, merge, reindex, rebalance, back up and replicate. Ask which hosts play which role before reading any host metric (RC p.2, p.27-28).
- **Where the work happens.**

  | Activity | Runs on | Disk I/O | CPU | Memory | Network |
  | --- | --- | --- | --- | --- | --- |
  | Ingest | D (tokenise on E unless fastload) | high, sequential flushes plus journal | high if transforms run | grows with in-memory stand, freed at flush | extra hop unless MLCP fastload |
  | Merge | D | high, background, sequential | moderate to high, shows as `nice` | low; spike at end if preload-mapped-data on | none unless NFS or similar |
  | Reindex | D | high | high | on D | none |
  | Rebalance | D (not background I/O) | high | high | not stated | not stated |
  | Backup / restore | D | high, competes with merge I/O | not stated | not stated | not stated |
  | Filtered search | D reads, E filters | high | high on E | tree caches | high |
  | Index resolution | D | via list cache or disk | positions/NEAR is costly | list cache, mapped indexes | not stated |
  | Server-side code, snippets, SPARQL/SQL joins | E | not stated | high | high (snippets read the whole document; SPARQL joins run in memory) | not stated |

  Condensed from RC p.4-7, 10, 27-28, 31 `[unverified — confirm for 11/12]`.
- **Normal, not a fault.** MarkLogic uses CPU and I/O when nobody is querying: spiky large sequential writes, background merge work shown as `nice` CPU, and memory growth during ingest are all expected. Do not call them the cause without a timing link to the complaint (RC p.4, 7).
- **Ingest path.** Journal write first (synchronous, must finish), document into the in-memory stand, flush to a new on-disk stand when full (stand directories are numbered hexadecimal), then merges combine stands. Under load two in-memory stands can exist at once. The in-memory structures favour ingest; the on-disk ones favour queries, so a bigger in-memory stand is not simply better when queries run during ingest (RC p.5-7).
- **Message names.** `XDMP-INMMTREEFULL`, `INMMLISTFULL`, `INMMINDXFULL`, `INMREVIDXFULL`, `INMTRPLIDXFULL` are informational: the in-memory stand filled and was written out. More often than about once a minute suggests raising the matching in-memory setting or adding hosts (RC p.6).
- **Merges.** Cost grows with the size of the stands merged and benefit with their number, so small stands merge with small ones. Every stand is assessed about once a second. The decision uses an estimate of the size after the merge (deleted fragments removed). A manual merge reduces a forest to the fewest stands the merge max size allows. A merge is also how deleted and replaced fragments free space (RC p.7-9).
- **Merge limits.** A forest can hold at most 64 stands; reaching that makes the database unavailable, so merges must keep up with ingest. The paper gives two usual reasons they do not: not enough I/O bandwidth, and a too-low `background-io-limit` (RC p.10 `[unverified — confirm for 11/12]`). The paper gives a 32 GB default merge max size; current documentation may differ `[unverified — confirm for 11/12]`.
- **Merge disk space.** Without HA or replication the paper says the free space needed is the indexed forest size plus 64 GB per forest (two merges of 32 GB); paused replication can need 2x to 4x the indexed data on the master; restoring into a live database 2x plus 64 GB per forest (RC p.7, 10 `[unverified — confirm for 11/12]`).
- **Merge I/O.** Sequential 512 KB units, not configurable; consider this when choosing stripe and block sizes. Merges are background I/O; the group `background-io-limit` throttles them in MB/s per host, normally unnecessary on direct-attached storage; 100 is the paper's starting point when merges lag on shared storage (RC p.10-11).
- **Merges and memory.** Preload-mapped-data loads all mapped pages (range indexes, lexicons) at the end of a merge; if they are no longer in the kernel buffer cache this shows as a burst of page faults and a memory spike (RC p.9-10).
- **Obsolete stands.** Directories holding an `Obsolete` file are normal while a merge, flush, running query or backup still needs the stand; they should only remain at startup after an unexpected stop or an unreachable network device (RC p.9-10).
- **Journal and locking.** The journal is written at transaction begin and commit. `journaling` `fast` survives a MarkLogic process stop; `strict` forces a filesystem sync and survives a machine crash, but is slower (shared-disk failover forces strict). Locks held too long can look like I/O contention; locking statistics are in Performance History (RC p.11, 34).
- **Fast data directory.** Optional per-forest SSD location for the journals, in-memory flushes and the smallest stands. SAS/SATA SSDs can write more slowly than disks as they fill and age; PCIe ones are generally fast. Measure sequential write throughput before recommending (RC p.11-12).
- **Indexes.** Universal index (terms, structure, optional phrases and positions), range indexes and lexicons (memory-mapped), reverse index, triple index. Every extra index setting costs ingest time, disk and CPU; range indexes and lexicons also cost memory. Tokenisation is language-specific, at load and at query time independently (RC p.13-17).
- **Index expansion.** Positions settings make a term list grow with every occurrence of a term, not just per document. Trailing wildcards add an entry per prefix of every long word; the three-character index adds trigrams and expands further. Field indexes are costly. The paper recommends this combination for arbitrary wildcards: word searches, three-character word searches, word positions, word lexicon (codepoint collation) and three-character word positions (RC p.15-17).
- **Estimating expansion.** Load at least 32 GB of representative content with the production index settings, detach and re-attach the forest to force a flush, and compare stand size to raw size. Raw size alone says nothing about disk use; keep room for deleted fragments (RC p.17).
- **Reindexing.** Adding a setting reloads the matching documents, then they merge. A new range index cannot be used by range queries until reindexing finishes, so raise reindex priority when it is needed urgently (RC p.30-31).
- **Query path.** App server, evaluator, broadcast to every D-node with a forest in the database. A D-node answers from the compressed tree cache or disk, resolves terms through the list cache or term files, uses memory-mapped indexes for ranges and lexicons, and includes the in-memory stand. The E-node expands compressed trees into the expanded tree cache, filters, aggregates, sorts and returns. Warm caches decide query speed (RC p.17-21).
- **Filtered vs unfiltered.** Index resolution on D-nodes finds candidate fragments; filtering on E-nodes opens each candidate to remove false positives. Unbounded filtered searches drive disk, network and E-node CPU and appear as long-running queries. `cts:search` is filtered unless told otherwise; the paper says client APIs such as Node.js and Java default to unfiltered (RC p.18-19, 27).
- **Caches.** List cache (term lists) and compressed tree cache (binary documents, large binaries in chunks) are D-node work; the expanded tree cache is E-node work; triple and triple-value caches grow and shrink on demand and matter only with semantics (internal databases such as Meters use triples). Large binaries never enter the expanded tree cache; external binaries are fetched by E-nodes (RC p.21-22).
- **Separated E/D sizing.** E-node group: raise the expanded tree cache. D-node group: raise list and compressed tree caches and cut the expanded tree cache sharply, but not to zero (reindexing and the Admin app on port 8001 need workspace). Default cache sizes assume a combined E/D host (RC p.21-22).
- **Cache partitions.** More partitions give more concurrency but smaller partitions; each ages out only its own entries. Too many reduces efficiency (RC p.21).
- **`xdmp:cache-status`.** Per host (optional host-id), per partition: size, table, busy, used, free, overhead. Busy, the share locked and not freeable, is the best predictor of a cache-full error. It can be costly, so run it sparingly. Current docs list compressed-tree, expanded-tree and list caches and require the status privilege (RC p.22-24; https://docs.marklogic.com/xdmp:cache-status). List, compressed and triple cache detail is also in `xdmp:forest-status` and the Admin UI.
- **Hits and misses.** Many expanded or compressed tree misses only mean many distinct documents are returned. Many list-cache or triple-cache misses mean those caches are too small or RAM is short (RC p.24).
- **Cache-full errors.** `XDMP-EXPNTREECACHEFULL` and `XDMP-LISTCACHEFULL` (names as in the paper; this skill's other notes also list `XDMP-TREECACHEFULL`, confirm which your version logs). A rare one means a query retried and succeeded and capacity planning is due; frequent ones are urgent (RC p.24-25 `[unverified — confirm for 11/12]`).
- **Memory consumers.** Range indexes and lexicons (mapped at mount or on demand), caches (allocated at start), the in-memory stand (as ingest proceeds), SPARQL in-memory joins. At startup the ErrorLog gives a recommended Huge Pages range: the low number is the sum of cache sizes, the high one adds forest in-memory settings. Disable Transparent Huge Pages; MarkLogic falls back to normal pages if Huge Pages are unavailable. The paper says RHEL, CentOS and SUSE support Huge Pages and Amazon Linux, Windows and macOS do not (RC p.31-32 `[unverified — confirm for 11/12]`; `memory-and-os.md` has the current sizing rule).
- **Swap.** Keep swap as protection. The paper's rule: swap equals RAM up to 32 GB RAM, otherwise 32 GB. Swapping is a critical symptom of too little memory (RC p.36).
- **Forests and topology.** Forests are the unit of concurrency; always more than one. The paper starts thinking about separate E/D nodes at about 16 hosts, and requires them for analytic or semantics work (64 GB or more RAM recommended on E-nodes there). Separation makes bottlenecks easier to read but is not mandatory; many 100+ host clusters are combined (RC p.25-28 `[unverified — confirm for 11/12]`).
- **Backup, journal archiving.** Backup is background I/O that competes with merges; throttle by scheduling backups and merge blackouts. Journal archiving adds load and longer restores; a `lag limit` (paper default 15 s, flush at least every 30 s) trades recovery point against throttling and memory (RC p.29-30).
- **HA memory.** After a failover a host may serve more primary forests than before; with preload off, memory and cache use can change sharply. Load-test failover. Local-disk failover costs extra disk, forests, CPU and memory for the replicas (RC p.33-34).
- **Cluster traffic.** Heartbeats between all hosts; a quorum is more than 50% of configured hosts (including down ones), so at least 3 hosts. Database replication between clusters uses XDQP (RC p.35).
- **App server threads and backlog.** Test with defaults, then raise threads while watching response time and throughput; a larger backlog queues requests cheaply and can match a high thread count. Size the backlog to about one second of expected requests (RC p.35-36).

## Standard procedures

1. Get the MarkLogic version, which hosts are E-nodes, D-nodes or both, forest count and RAM per host. Remember the paper covers 7/8.
2. Pin the complaint to a resource using host metrics first (`sar-analysis.md`; ask for SAR with `performance-data-requests.md`): disk busy, CPU split, memory and swap, network. Do this per role: E-node CPU or D-node disk answers different questions.
3. Match the pattern. Low disk and high CPU: tune code or query, add E-node cores (RC p.28). High disk and low CPU: improve storage or add D-nodes, and consider E/D separation (RC p.28-29). Swapping: memory shortage, not a tuning knob (RC p.36).
4. Check what background work ran at the time: merges (`nice` CPU, I/O bursts, stand count against 64), reindex, rebalance, backup, journal archiving. Read the ErrorLog for `Info` merge, in-memory and cache messages around the complaint time (`log-anatomy.md`).
5. Caches: run `xdmp:cache-status` on the affected hosts (sparingly) and read `partition-busy` and `partition-free`. Count cache-full errors in the ErrorLog: occasional, or frequent.
6. Filtering and result size: ask whether the slow requests are filtered and unbounded and how many documents they return; confirm with `xdmp:query-meters` and `performance-tuning.md`.
7. Merge health: stand counts per forest, merge max size, `background-io-limit`, blackouts, free disk against the merge-space rule above.
8. Memory: startup Huge Pages recommendation in the ErrorLog against what is configured, THP disabled, swap present, range indexes and preload setting (`memory-and-os.md`).
9. State the finding as mechanism plus evidence plus a remediation from the table below. Say that capacity decisions need tests with representative data, queries and hardware, as the paper itself warns. Mark every number `[unverified — confirm for 11/12]` unless checked.

## Common mistakes & symptoms

| Mistake | Symptom seen by customer | How to confirm | Fix / best practice | Source |
| --- | --- | --- | --- | --- |
| Blaming merge or ingest activity for load that is normal | Customer sees `nice` CPU and spiky disk writes with no queries running | Compare timing with the complaint; `nice` share in SAR; merge messages in ErrorLog | Treat as normal unless it coincides with slowness; if it does, look at I/O capacity and background limits | Resource Consumption p.4, 7 |
| Merges cannot keep up with ingest | Stand count climbs toward 64, updates slow or stop, "approaching maximum stands" warnings | Stand count per forest; merge max size, `background-io-limit`, blackout windows, disk throughput | Remove a too-low background limit, add I/O bandwidth, or slow ingest; also check merge max size, blackout windows and that merges are enabled (current-documentation checks, not from the paper) | Resource Consumption p.10 `[unverified — confirm for 11/12]` |
| Too little free disk for merges, HA or restore | Merges stall, forest runs out of space | Free space against indexed size plus the per-forest merge allowance; replication state | Keep the headroom (paper: indexed size + 64 GB per forest, more with paused replication or restore) | Resource Consumption p.7, 10 `[unverified — confirm for 11/12]` |
| Setting `background-io-limit` on direct-attached storage by default | Merges lag for no obvious reason | Group setting value against disk capability | Use only when merges themselves hurt; start near 100 MB/s on shared storage | Resource Consumption p.11; https://docs.marklogic.com/admin:group-set-background-io-limit |
| Filtered, unbounded searches | Long-running queries, high disk and E-node CPU, heavy network | Long-running requests; `xdmp:query-meters`; code shows `cts:search` with no `"unfiltered"` | Use unfiltered where false positives are tolerable or fix index settings; bound result size | Resource Consumption p.18-19 |
| Cache sizes left at combined-host defaults on separated E/D groups | Cache-full errors or misses on one role | `xdmp:cache-status` per host; group cache settings | Raise expanded tree cache on E-nodes; list and compressed tree on D-nodes | Resource Consumption p.21-22 |
| Frequent cache-full errors ignored | Intermittent failed requests, slow cluster | Error rate per hour in ErrorLog; `partition-busy` high | Shrink or bound the result, tune the query, add memory or hosts, or fewer partitions as a late step | Resource Consumption p.24-25 `[unverified — confirm for 11/12]` |
| Too many cache partitions | Cache fills despite free memory | Partition count against size | Fewer, larger partitions (less concurrency) | Resource Consumption p.21, 24 |
| Switching on every index setting | Slow ingest, large indexes, heavy reindex | Index settings against queries actually run | Enable only what queries need; test expansion with representative data | Resource Consumption p.15-17 |
| Wildcard or positions indexes on large text | Disk grows far beyond raw size | Index settings; stand size against raw size | Prefer the paper's wildcard index set; avoid trailing wildcards unless needed | Resource Consumption p.15-17 |
| Reindexing during peak with default priority | Query slowdown for hours after an index change | Reindex activity and merge load in ErrorLog and SAR | Lower reindexer throttle (paper example 3) and set a background limit; schedule off peak; disable and resume | Resource Consumption p.30-31 `[unverified — confirm for 11/12]` |
| Forgetting rebalance is not background I/O | Disk and CPU load after adding hosts | Rebalancer activity | Use the rebalance throttle and quiet times | Resource Consumption p.31 |
| Backups overlapping merges | Disk saturated at backup time | Backup schedule against merge activity | Schedule backups and merge blackouts apart | Resource Consumption p.29 |
| Journal archiving lag limit too low for the archive disk | Writes throttled | Lag limit and archive I/O | Raise the lag limit if recovery point allows; give the archive faster storage | Resource Consumption p.29-30 |
| Strict journaling or shared-disk failover not considered | Slower updates than expected | Journaling setting; failover type | Know that strict adds a sync per commit; weigh against safety | Resource Consumption p.11, 34 |
| Long-held locks read as I/O trouble | Slow updates, disk looks fine | Locking statistics in Performance History | Shorten transactions; check lock waits before storage | Resource Consumption p.11 |
| Huge Pages not configured, or Transparent Huge Pages left on | Memory overhead or stalls | Startup ErrorLog recommendation against configured; THP setting | Configure the logged range; disable THP | Resource Consumption p.31-32 `[unverified — confirm for 11/12]` |
| Running with no swap, or swapping | OOM kills, or severe slowdown | SAR swap and memory; `free` | Add swap per rule; fix the memory shortage | Resource Consumption p.36 |
| Performance test never run through a failover | Cache-full or OOM after a host fails | Memory per host after reassignment | Load-test failover; size for the heavier host | Resource Consumption p.33 |
| App server threads or backlog never tuned | Timeouts or poor throughput under load | Threads and backlog; response time against throughput | Measure, then raise threads; set backlog to about one second of requests | Resource Consumption p.35-36 |
| Combined E/D at large scale with unexplained bottlenecks | Hard to tell which role is saturated | Per-host metrics | Consider separating E and D nodes to isolate load | Resource Consumption p.26-29 `[unverified — confirm for 11/12]` |
