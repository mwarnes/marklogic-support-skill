# External authentication troubleshooting — LDAP, client certificates, OAuth 2.0, SAML, HTTPS/TLS, Kerberos

Distilled from the maintainer's Security Hub (https://mwarnes.github.io: the Diagnostics pages, the how-to guides and the LDAP, SAML, OAuth 2.0, Kerberos and TLS articles, read 2026-11-05). It is a personal collection, **not** official Progress or MarkLogic documentation. Its facts were tested by the maintainer on MarkLogic 11.3.7 and 12.1.0 (against authentik, 389-ds and a test CA) unless a row says otherwise; say "tested by the maintainer" when you quote them. The Security database and its external security objects are **not in the support dump**, so this data is collected with the gather script or the Management API: see `security-data-requests.md`. A report from the gather script is read with the procedure below. Check the security incident gate (`security-vulnerability-handling.md`) first; a flood of failed logins or an unknown account logging in is an incident signal, not a configuration fault.

## Concepts

- **Two decisions, kept apart.** Authentication (who is this?) and authorization (which roles?). A good bind, token or certificate does not prove the role mapping. `401` or `500` is usually authentication; `403` after a passed login is usually authorization (`SEC-PRIV` in the case of OAuth).
- **The objects.** An *external security profile* (`/manage/v2/external-security`) with `authentication` (`ldap`, `certificate`, `oauth`, `saml`; Kerberos is separate, below) and `authorization` (`internal`, `ldap`, `saml`, `oauth`), bound to an app server (`external-security` property, with the app server's `authentication` set to match); an HTTPS app server also needs a certificate template. Names of roles and users are in the Security database.
- **External names.** The link between the outside world and a role or user. Role external names are matched case-insensitively and are **cluster-wide** (two roles with one external name both grant). User external names (LDAP authorization `internal`, certificate authorization `internal`) are matched case- and space-sensitively.
- **Cache.** Results are cached per profile for `cache-timeout` seconds (default 300; LDAP failures use `ldap-negative-cache-timeout`). A retry inside the window can write **no trace lines** and seem to ignore a fix. Set it to `1` while testing.
- **Trace events** (Group › Diagnostics, ErrorLog at Info level) show each step: `External Authenticate` (every external login), `LDAP`, `LDAP Search`, `SAML`, `SAML Response`, `OAuth`, `OAuth Status`, `OAuth Communications`, `OAuth JSON Processing`. `ml-trace-events.py` has presets `saml`, `oauth`, `ldap`, `certificate` (`External Authenticate` only; add the `ldap` events for authorization `ldap`). Group properties hold a flat `event` list and a `PUT` **replaces** the whole list, so never hand-write that call for a customer: use the script or the Admin UI. Disable them afterwards.
- **The ErrorLog does not say which app server a line belongs to.** If several app servers use external security, reproduce one login at a time. Log times are in each host's local time zone; the gather's `--start`/`--end` are UTC.
- **What can never be seen from MarkLogic:** a client certificate rejected in the TLS handshake (nothing in ErrorLog or AccessLog); the IdP's own log (redirect URI and ACS errors are shown only at the IdP); the directory's group membership; whether a refused LDAP bind (error 49) was the search account or the user.
- **MarkLogic 11.3 limits (tested):** its HTTPS client cannot reach an IdP endpoint that needs TLS 1.3 or the extended master secret (`SVC-SOCCONN`; authentik is one); it serves no TLS 1.3. MarkLogic 12.1 has `ssl-min-allow-tls`. OAuth Authorization code is MarkLogic 12 only (11 supports Resource server only).
- **Kerberos has no gather area and the maintainer's Kerberos article is untested on 11 and 12.** Treat every Kerberos statement here as `[unverified — confirm]`.

## Standard procedures

1. **Pin down the scheme and the symptom.** Ask: MarkLogic version; which scheme (LDAP, certificate, OAuth Resource server or Authorization code, SAML, Kerberos); the app server name and group; the exact HTTP status and ErrorLog text; whether the browser reaches the IdP; one failing user and one working user; time (UTC) of one failing attempt; any proxy or load balancer in front (SAML and OAuth Authorization code keep per-request state on the node that started the login, see `ticket-auditing.md`).
2. **Separate the layer.** Browser or client → TLS to the app server (`https` area) → profile found on the app server → authentication against the IdP or directory → mapping to a user → role mapping (403). Ask which layer, then use the matching rows below.
3. **Get the data** from `security-data-requests.md`: the gather script for the scheme, or the manual Management API route. Ask for one area at a time. Always ask for the exact reproduction time so `--start` can be used.
4. **Read a gather report** (`SUMMARY.md`): (a) the **Conclusion** line: "All good", "No failure found. N warning(s)" or "Root cause to look at first: ..." (later failures are often consequences of the first; "Probable cause" is a lead from the logs, not a confirmed cause); (b) **Check results** (`PASS`/`WARN`/`FAIL`/`INFO`, failures first); (c) **Not collected**: a verdict covers only what was collected, so ask for the missing part (for example `--token`, `--logs`, `--saml-response`, `--idp-metadata`, `--client-cert`) before concluding; (d) **Log findings**. Open the raw JSON only for an exact value.
5. **Rank causes** with the rows below; for each give the confirming check. A "mapped to no role" cause is confirmed by the AccessLog line `External User(x) is Mapped to Temp User(x) with Role(s): ...` (empty list = no role matched).
6. **Run the directory or IdP commands the report prints** (the script never queries the directory): `ldapsearch`, `ldapwhoami` (two commands: search account, then user), `openssl s_client`. Ask the customer to run them and send the output.
7. **Fix, then retest** with a user that has not logged in recently, or after `cache-timeout`. Turn the trace events off.

## Common mistakes & symptoms

| Mistake | Symptom seen by customer | How to confirm | Fix / best practice | Source |
| --- | --- | --- | --- | --- |
| LDAP: wrong `ldap-base` or `ldap-attribute` (for example `uid` against Active Directory) | `401`; ErrorLog `ldapAuthenticate() fail because authentication failure` or `... no LDAP user`, no error 49 beside it | The search finds no entry: run `ldapsearch` with the exact base, attribute and user name; the gather says "no bind failed: the search found no entry" | Correct the base or use `sAMAccountName` on Active Directory | <https://mwarnes.github.io/scripts-browser/diagnostics/ldap/> |
| LDAP: search account or user password refused | `401`; `XDMP-LDAP-INVALID-CRED: ldap_simple_bind_s failed ... Invalid credentials (49)` | ErrorLog is identical for both binds: run the two `ldapwhoami` commands the gather prints, or read the directory's access log | Fix the search account (`ldap-default-user`, `ldap-password`) or the user's password | <https://mwarnes.github.io/scripts-browser/diagnostics/ldap/> |
| LDAP: authorization `internal` but the user's external name is not the full DN | `401`; bare `ldapAuthenticate() fail`, directory side fine | MarkLogic user's `external-names` (`GET /manage/v2/users/<u>/properties`) is a short name | Set the external name to the full DN (`uid=jdoe,dc=example,dc=com`) | <https://mwarnes.github.io/scripts-browser/diagnostics/ldap/> |
| LDAP: bind method `external` for password logins | `ldapAuthenticate() fail because authentication failure` and the directory shows **no connection** from MarkLogic | Directory access log for the same second has nothing; profile `ldap-bind-method` | Use `simple`; read the directory log with buffering off (389-ds buffers its access log by default) | <https://mwarnes.github.io/articles/LDAP-TROUBLESHOOTING.html> |
| LDAP: authorization `ldap` and no role external name equals the user's group DN | `200` login then `403` | `ldapsearch` for the user's `memberOf` values; compare with every role's external name (`roles-external-names.json` in the gather); the gather WARNs on a near miss (same DN, other suffix) | Make a role's external name equal the group DN exactly (case does not matter) | <https://mwarnes.github.io/scripts-browser/diagnostics/ldap/> |
| LDAP: wrong port or scheme (`ldaps://` on 389, host name does not resolve) | Login hangs, or `401` every time | Gather FAILs "does not answer on port N", "host name does not resolve" or "TLS on connect does not work on port 389" (probe from the gather host, so also check from a MarkLogic host) | `ldap://` with StartTLS on 389 or `ldaps://` on 636; correct the name | <https://mwarnes.github.io/scripts-browser/diagnostics/ldap/> |
| LDAP: `ldap-start-tls` false on `ldap://` | Works, but the password crosses the network in clear text | Profile property, gather WARN | Set `ldap-start-tls` true or use `ldaps://` | <https://mwarnes.github.io/scripts-browser/diagnostics/ldap/> |
| App server has no external security profile selected (any scheme) | `401` with a correct profile; ErrorLog `externalAuthenticate failed because no external security is configured` | `GET /manage/v2/servers/<name>/properties?group-id=<g>`: property `external-security`; gather `--appserver` FAILs | Select the profile; set the app server's `authentication` to match the scheme | <https://mwarnes.github.io/articles/LDAP-TROUBLESHOOTING.html> |
| Certificate: issuing CA trusted by MarkLogic but not **selected** for the app server; intermediates missing when issuer verification is off | TLS alert `unknown ca` (curl `(56)`/reset, no HTTP status); nothing in ErrorLog or AccessLog | App server `ssl-client-certificate-authority` (ids) and `ssl-client-issuer-authority-verification`; with verification false select the root and every intermediate, with true the issuing CA alone | Select the CAs (Admin UI App Server › SSL Client Certificate Authorities, or the property) | <https://mwarnes.github.io/scripts-browser/diagnostics/certificate-internal/> |
| Certificate: expired, not yet valid or `serverAuth`-only (no `clientAuth`) certificate | TLS alerts `certificate expired` (45) or `unsupported certificate` (43); nothing logged | `openssl x509 -in client.pem -noout -dates -ext extendedKeyUsage`; `curl -v` or `openssl s_client` shows the alert (browsers hide it) | Reissue with `clientAuth` and valid dates | <https://mwarnes.github.io/scripts-browser/diagnostics/certificate-internal/> |
| Certificate, authorization `internal`: external name is a CN, reordered, has spaces after commas or another case | `401`; `certificateAuthenticate() fail because no user` and `External authentication failed: user= dn=<DN>` | The `dn=` value is what MarkLogic looked up: compare with the user's external name character by character (match is case- and space-sensitive) | Copy the `dn=` value into the user's external name (stored order, commas without spaces) | <https://mwarnes.github.io/articles/LDAP-TROUBLESHOOTING.html> |
| Certificate: no external security profile on the app server, user has the DN as external name | `401`; `externalAuthenticate failed because no external security is configured` | Tested 11.3.7 and 12.1.0: without a profile MarkLogic maps the certificate's **CN to a user name**; external names are not used | Create a user named like the CN, or add the profile and use the full DN as external name | <https://mwarnes.github.io/scripts-browser/diagnostics/certificate-internal/> |
| Certificate, authorization `ldap`: DN stored general-first (`DC=com,DC=example,...`, typical of enterprise CAs) | `401`; `certificateAuthenticate() fail because unknown user, dn DC=com,...` | MarkLogic does a base-scope LDAP search with the DN as stored (`ldap-base` unused); the gather shows the DN and its reverse and prints an `ldapsearch` | Reissue the certificate with the DN in LDAP order (most specific first) | <https://mwarnes.github.io/scripts-browser/diagnostics/certificate-ldap/> |
| Certificate with LDAP: entry missing, attribute missing or search account cannot read it | Same `unknown user` line with a right-looking DN | Four causes write one line; run the printed `ldapsearch` as the search account and again as an administrator | Create the entry, correct `ldap-attribute`, or grant read access | <https://mwarnes.github.io/scripts-browser/diagnostics/certificate-ldap/> |
| Client certificate not required (`ssl-require-client-certificate` false) or authentication `basic` | A client with no certificate gets `401` instead of a TLS failure; certificates are ignored | App server properties; gather INFO or WARN | Set `ssl-require-client-certificate` true and authentication `certificate` | <https://mwarnes.github.io/scripts-browser/diagnostics/certificate-internal/> |
| OAuth: `oauth-jwt-issuer-uri` differs from the token's `iss` (often a trailing `/`) | `500`; `JWT issuer URI validation fails. Expected ... Received ...` | Compare the profile with the discovery document's `issuer` and the token's `iss` (gather `--token`) | Copy the issuer exactly from discovery | <https://mwarnes.github.io/scripts-browser/diagnostics/oauth-resource-server/> |
| OAuth: `oauth-client-id` is neither `aud` nor `azp` of the token; token expired (about 5 minutes of skew tolerated) | `500`; `JWT client id validation fails` or `JWT verification failed ... token expiration` | Decode the token claims (gather `--token` checks both) | Use the client id the token was issued to; request a new token | <https://mwarnes.github.io/scripts-browser/diagnostics/oauth-resource-server/> |
| OAuth: `oauth-jwks-uri` wrong | `500`; `invalid json`, JWKS response is HTML or HTTP 404 | Fetch the JWKS URI from a MarkLogic host; gather detects HTML or 404 | Correct the URI from discovery | <https://mwarnes.github.io/scripts-browser/diagnostics/oauth-resource-server/> |
| OAuth: role claim not mapped (wrong `oauth-role-attribute`, claim absent, scope missing) | `403` (`SEC-PRIV`) with a valid token; the trace line `Roles: [...]` lists claim values, **not** granted roles | Gather FAIL "role claim values map to a MarkLogic role" names another claim that matches; AccessLog `Mapped to Temp User ... Role(s):` | Set `oauth-role-attribute`, add the roles scope at the IdP, or fix the role's external name | <https://mwarnes.github.io/scripts-browser/diagnostics/oauth-resource-server/> |
| OAuth on MarkLogic 11.3: IdP needs TLS 1.3 or the extended master secret, or its CA is not trusted | `500`; `XDMP-OAUTH: SVC-SOCCONN` fetching discovery or keys | Gather FAILs when `openssl s_client -tls1_2 -no_ems` against the IdP is refused; compare the IdP chain with `GET /manage/v2/certificate-authorities` | Trust the IdP's CA, use MarkLogic 12, or put a compatible TLS endpoint in front of the IdP | <https://mwarnes.github.io/howto/oauth2-resource-server/> |
| OAuth Authorization code: redirect URI at the IdP is not exactly `https://host:port` (no path) | IdP shows a redirect URI error and never returns; MarkLogic only logs the redirect (gather: Probable cause) | The IdP's page and log (MarkLogic cannot see them); `oauth-redirect-uri` in the profile | Register exactly the app server address | <https://mwarnes.github.io/scripts-browser/diagnostics/oauth-authorization-code/> |
| OAuth Authorization code: IdP client does not allow the `authorization_code` grant; wrong client secret; wrong token or authorization endpoint | `500` with `OAuth Error: 'invalid_request'` right after the redirect; or `invalid_client` (HTTP 400) at the code exchange; or an HTML page from the token endpoint | ErrorLog `OAuth Status` lines; compare `oauth-token-server-uri` and `oauth-authorization-server-uri` with discovery (the client secret is write-only and cannot be compared) | Enable the grant at the IdP; correct secret and endpoints | <https://mwarnes.github.io/scripts-browser/diagnostics/oauth-authorization-code/> |
| OAuth Authorization code on an HTTP app server or on MarkLogic 11 | The redirect never happens, or the profile cannot be created | App server has no certificate template while the redirect URI is https (gather FAIL); version | HTTPS is required in production; Authorization code needs MarkLogic 12 | <https://mwarnes.github.io/howto/oauth2-authorization-code/> |
| OAuth Authorization code: expecting a clean log | Every login logs `External authentication failed: user=` and `getRedirectURI() ... stateVal: (empty)` for the first request | Normal; the gather does not count them | None; do not report as the cause | <https://mwarnes.github.io/howto/oauth2-authorization-code/> |
| SAML: stored IdP certificate is not the one the IdP signs with (renewed, or per application, or the encryption key was stored) | `401` or `500`; `Saml Response Error: signature is invalid` | Compare `saml-idp-certificate-authority` SHA-1 with the metadata's signing certificate (gather `--idp-metadata`) | Store the IdP's current **signing** certificate | <https://mwarnes.github.io/scripts-browser/diagnostics/saml/> |
| SAML: `saml-entity-id` or `saml-issuer` wrong | `Issuer ... does not match configured IdP` or `Audience ... does not match SP entity ID` | `saml-entity-id` must equal the metadata entityID; `saml-issuer` is the SP entity id: the app server address **without** a path or trailing slash | Correct both; `saml-destination` is the IdP's HTTP-Redirect sign-in URL of this application | <https://mwarnes.github.io/scripts-browser/diagnostics/saml/> |
| SAML: ACS URL registered at the IdP without the trailing slash, or audience with it | Browser stops at the IdP with an ACS or audience error; MarkLogic logs nothing useful | Visible only at the IdP | Register ACS `https://host:port/` (with slash) and audience `https://host:port` | <https://mwarnes.github.io/howto/saml/> |
| SAML: no role external name equals a `Group` value of the assertion (or the assertion has no group attribute) | Sign-in succeeds then `403`; AccessLog `Mapped to Temp User(x) with Role(s):` empty | Gather FAIL "Group values map to a MarkLogic role" (closest names listed); roles come only from the assertion, not from the MarkLogic user's roles or external names | Create or correct the role external name (one-character differences are common); add the group attribute at the IdP | <https://mwarnes.github.io/scripts-browser/diagnostics/saml/> |
| SAML: app server authentication is not `saml`, or an https issuer on an HTTP app server | Never sent to the IdP (`401` with a basic-auth challenge), or the browser stops at the IdP | Gather WARN/FAIL on the app server; certificate template present? | Set authentication `saml`; give the app server a template | <https://mwarnes.github.io/scripts-browser/diagnostics/saml/> |
| SAML: load balancer without stickiness (SP-initiated state is node-local) | Intermittent failures; AuthnRequest and SAMLResponse hit different nodes | AccessLog of each node, see `ticket-auditing.md` | Sticky routing | <https://mwarnes.github.io/articles/SAML-TROUBLESHOOTING.html> |
| SAML: SP private key does not match the SP certificate | Nothing, until an IdP requires signed requests | Not detectable: MarkLogic returns the key encrypted; compare the certificate's public-key SHA-256 (gather prints it) with `openssl pkey -in sp.key -pubout -outform der \| openssl dgst -sha256` | Replace the pair | <https://mwarnes.github.io/scripts-browser/diagnostics/saml/> |
| HTTPS: host name not in the certificate's SANs | Browser name warning; `curl: (60)` | Gather FAIL "certificate matches host name" (use `--probe-host` for the name clients use) | Reissue with the name as a SAN | <https://mwarnes.github.io/scripts-browser/diagnostics/https/> |
| HTTPS: template holds only the TEMPORARY self-signed certificate, or no certificate | Clients distrust it; ErrorLog `Failed to find server certificate in certificate template <id>` (template created through the API holds none until a certificate is imported) | `GET /manage/v2/certificates/<id>` field `temporary`; gather labels TEMPORARY or PERMANENT | Create a CSR on the template, have it signed, import it | <https://mwarnes.github.io/scripts-browser/diagnostics/https/> |
| HTTPS: only the leaf is served (issuing CA not in MarkLogic's trusted authorities) | Some clients: `unable to verify the first certificate` (`openssl` return code 21) | Gather WARN "server sends only its own certificate" | Tested on 12.1.0: import the issuing CA as a trusted CA (`pki:insert-trusted-certificates`); the port then sends leaf + intermediate with no restart. A bundle in the certificate import is rejected (`PKI-BADCERTIFICATE`) | <https://mwarnes.github.io/scripts-browser/diagnostics/https/> |
| HTTPS: old protocols allowed | Scanner findings (`TLSv1` accepted) | Gather WARN; 11 uses `ssl-disable-*` flags, 12 uses `ssl-min-allow-tls` and `ssl-ciphersuites` | Set the minimum to TLS 1.2; MarkLogic 11.3 has no TLS 1.3 | <https://mwarnes.github.io/scripts-browser/diagnostics/https/> |
| Kerberos: `services.keytab` missing, unreadable or on the wrong node | Authentication fails at once, or only some requests fail (only some backend nodes) | `[unverified — confirm]` Per the article: file in the host's data directory readable by the MarkLogic account; `klist -kte`; compare every node and the load balancer name | Install on every node that can handle the request, mode 600 | <https://mwarnes.github.io/articles/KERBEROS-TROUBLESHOOTING.html> |
| Kerberos: key version mismatch, wrong or duplicate SPN, clock skew, no route to the KDC | `KRB_AP_ERR_BADKEYVER`, `KRB_AP_ERR_SKEW`, no service ticket, timeouts (library wording, not necessarily MarkLogic's) | `[unverified — confirm]` `kvno HTTP/<name>@REALM` vs `klist -kt`; `timedatectl`, `chronyc tracking`; `nc -zv <kdc> 88` | Regenerate the keytab, correct the SPN, fix time sync, open ports 88 and 464 | <https://mwarnes.github.io/articles/KERBEROS-TROUBLESHOOTING.html> |
